# L2 Mechanism Guide: How LLM Inference Works

This guide explains the mechanisms implemented in [`L2.ipynb`](L2.ipynb).
The emphasis is not on using a high-level serving API. It is on understanding
what happens inside a decoder-only language model as it turns a prompt into new
tokens, and exactly what changes when a KV cache is enabled.

## The complete inference loop

Given this prompt:

```text
SGLang is a fast inference engine for
```

the model generates one token at a time:

```text
prompt -> tokenize -> model forward -> logits -> choose token -> append -> repeat
```

For greedy decoding, the repeated operation is:

$$
t_{n+1} = \arg\max_v f_\theta(t_1, \ldots, t_n)[v]
$$

where:

- $t_1, \ldots, t_n$ are the token IDs seen so far.
- $f_\theta$ is the language model.
- The model returns one score, or logit, for every vocabulary token.
- $v$ indexes the vocabulary.
- `argmax` selects the highest-scoring next token.

The selected token is appended to the sequence, so the next model call has one
more token of context. Text generation is therefore repeated next-token
classification with a growing input.

## 1. Tokenization: text becomes model input

A language model does not directly receive words or characters. The tokenizer
maps text to integer IDs from a fixed vocabulary:

$$
\text{text} \xrightarrow{\text{tokenizer}} [t_1, t_2, \ldots, t_P]
$$

The L2 prompt becomes nine token IDs. A token may be:

- A complete word.
- Part of a word.
- Punctuation.
- A piece that includes a leading space.

The model uses each ID to select an embedding vector. If the hidden dimension is
$D$, the prompt embedding tensor has shape:

```text
[batch, sequence, hidden] = [1, 9, D]
```

Tokenization matters for inference cost because model work scales with token
positions, not with the number of human-readable words.

## 2. One transformer layer

A decoder-only model contains a stack of transformer layers. At a high level,
each layer performs:

```text
hidden states
    -> normalization
    -> causal self-attention
    -> residual connection
    -> normalization
    -> feed-forward network
    -> residual connection
```

Self-attention mixes information across sequence positions. The feed-forward
network transforms each position independently. After all layers, the model
projects the final hidden state to vocabulary logits.

Only the logits at the final sequence position are needed to choose the next
token:

```python
next_token_logits = outputs.logits[:, -1, :]
```

If the vocabulary contains $V$ entries, this tensor has shape `[1, V]`.

## 3. Query, key, and value tensors

Inside each attention layer, hidden states are projected into query, key, and
value tensors:

$$
Q = XW_Q, \qquad K = XW_K, \qquad V = XW_V
$$

Their conceptual roles are:

- **Query:** What information is this position looking for?
- **Key:** What information does each earlier position advertise?
- **Value:** What information should be returned if a key is relevant?

Typical tensor shapes are:

```text
Q: [batch, query_heads, query_length, head_dim]
K: [batch, kv_heads,    key_length,   head_dim]
V: [batch, kv_heads,    key_length,   head_dim]
```

For full prompt processing, `query_length == key_length`. During cached decode,
`query_length` is usually 1 while `key_length` contains the complete prefix.

## 4. Scaled dot-product attention

The core attention equation is:

$$
\operatorname{Attention}(Q,K,V) =
\operatorname{softmax}\left(\frac{QK^T}{\sqrt{d_k}} + M\right)V
$$

L2 translates this directly into PyTorch.

### Step 1: compare queries with keys

```python
scores = torch.matmul(q, k.transpose(-2, -1))
```

For each query position, this computes a similarity score against every key
position. The resulting shape is:

```text
[batch, heads, query_length, key_length]
```

### Step 2: scale the scores

```python
scores = scores * (1.0 / math.sqrt(head_dim))
```

Dot-product magnitude tends to grow with the vector dimension. Dividing by
$\sqrt{d_k}$ keeps softmax inputs in a useful numerical range.

### Step 3: apply the causal mask

A token must not read future tokens. For a sequence of length four, the allowed
attention pattern is:

```text
query 0: key 0
query 1: key 0, 1
query 2: key 0, 1, 2
query 3: key 0, 1, 2, 3
```

Disallowed scores are replaced with negative infinity:

```python
scores = scores.masked_fill(~mask, float("-inf"))
```

After softmax, those positions receive probability zero.

### Step 4: normalize

```python
probabilities = torch.softmax(scores, dim=-1)
```

Each query's scores become a probability distribution over visible key
positions.

### Step 5: combine values

```python
output = torch.matmul(probabilities, value)
```

The output for each query is a weighted sum of value vectors. This is how one
token position retrieves relevant information from its prefix.

## 5. Why the cached mask is bottom-right aligned

For normal full-sequence attention, query and key lengths are equal, so a simple
lower-triangular mask works.

Cached decode is different:

```text
query_length = 1
key_length   = length of the complete prefix
```

Suppose the cache contains five positions and the model is processing the sixth
token. The one query represents absolute position 5, not position 0. It must be
allowed to attend to keys 0 through 5.

L2 assigns query positions from the right edge of the key sequence:

```python
query_positions = torch.arange(
    key_length - query_length,
    key_length,
)
key_positions = torch.arange(key_length)
mask = key_positions[None, :] <= query_positions[:, None]
```

This is called bottom-right causal alignment. It works for both equal lengths
and a short query attending to a longer cached prefix.

## 6. Grouped-query attention

Some models use fewer key/value heads than query heads. If a model has 32 query
heads and 8 KV heads, four query heads share each KV head:

$$
\text{group size} = \frac{H_Q}{H_{KV}} = \frac{32}{8} = 4
$$

This is grouped-query attention (GQA). It reduces KV-cache memory because the
model stores 8 K heads and 8 V heads rather than 32 of each.

The educational implementation repeats K and V heads to match Q:

```python
group_size = query.shape[1] // key.shape[1]
key = key.repeat_interleave(group_size, dim=1)
value = value.repeat_interleave(group_size, dim=1)
```

This makes the mechanism visible but physically copies tensors. Production
kernels support grouped heads without materializing those copies.

## 7. Autoregressive decoding without a KV cache

The uncached loop in [`helper.py`](helper.py) is conceptually:

```python
token_ids = tokenize(prompt)

for step in range(max_new_tokens):
    logits = model(all_token_ids_so_far, use_cache=False)
    next_token = sample(logits)
    token_ids.append(next_token)
```

At every step, the model receives the complete sequence again.

For a three-token prompt generating four tokens, the evaluated lengths are:

```text
step 1: 3 positions
step 2: 4 positions
step 3: 5 positions
step 4: 6 positions
total:  18 position evaluations
```

The model recomputes hidden states, Q, K, V, attention, and feed-forward results
for old positions even though those prefix tokens have not changed.

For prompt length $P$ and generated length $N$:

$$
E_{\text{uncached}}
= \sum_{i=0}^{N-1}(P+i)
= NP + \frac{N(N-1)}{2}
$$

With the L2 values $P=9$ and $N=16$:

$$
E_{\text{uncached}} = 16(9) + \frac{16(15)}{2} = 264
$$

## 8. What the KV cache contains

At each transformer layer, K and V for existing tokens remain valid during later
decode steps. Their values depend on the fixed prefix representations at that
layer; appending a future token does not change earlier causal states.

The cache stores the K and V tensors from every layer:

```text
layer 0: K prefix, V prefix
layer 1: K prefix, V prefix
...
layer L: K prefix, V prefix
```

A simplified cache-size equation is:

$$
M_{KV} =
2 \times L \times B \times H_{KV} \times T \times D_h \times S
$$

where:

- $2$ represents K and V.
- $L$ is the number of layers.
- $B$ is batch size.
- $H_{KV}$ is the number of KV heads.
- $T$ is cached sequence length.
- $D_h$ is head dimension.
- $S$ is bytes per element.

The cache trades memory for less recomputation. Its size grows linearly with
sequence length and batch size.

## 9. Prefill: creating the initial cache

Cached generation begins by sending the complete prompt through the model once:

```python
logits, cache = model.forward_raw_with_kv_cache(prompt_token_ids)
```

This call does two things:

1. Produces the logits used to select the first generated token.
2. Returns K/V tensors for all prompt positions at every layer.

The prompt positions are processed in parallel. This stage is called **prefill**.
Its duration contributes to time to first token.

For L2, prefill evaluates all nine prompt positions once.

## 10. Decode: extending the cache one token at a time

After prefill, each step sends only the newest token plus the existing cache:

```python
logits, cache = model.forward_raw_with_kv_cache(
    [latest_token_id],
    past_key_values=cache,
)
```

Within each layer:

1. Compute Q, K, and V for the new token.
2. Append the new K and V to that layer's cache.
3. Compare the new Q with all cached K vectors.
4. Use attention probabilities to combine all cached V vectors.
5. Pass the new position through the rest of the layer.

Old token positions are not passed through the model again.

The position-evaluation count becomes:

$$
E_{\text{cached}} = P + (N-1)
$$

The first generated token comes from prefill logits, so only the remaining
$N-1$ generated tokens require separate one-position forwards.

For $P=9$ and $N=16$:

$$
E_{\text{cached}} = 9 + 15 = 24
$$

Compared with the uncached path:

$$
\frac{264}{24} = 11
$$

L2 therefore performs 11 times fewer model token-position evaluations with the
cache.

## 11. What the KV cache does not eliminate

The new query still attends to every cached key. As the sequence grows, each
decode step reads a longer prefix:

```text
decode step 1: one query attends to P keys
decode step 2: one query attends to P + 1 keys
decode step 3: one query attends to P + 2 keys
```

It is useful to distinguish two complexity measures:

| Measure | Without cache | With cache |
|---|---:|---:|
| Model token-position evaluations | $O(N^2)$ | $O(N)$ after prefill |
| Cumulative attention arithmetic | $O(N^3)$ | $O(N^2)$ |
| Retained KV memory | None | $O(N)$ |

The cache avoids recomputing old positions. It does not make long-context
attention constant-time.

## 12. Why cached and uncached output must match

Both paths implement the same causal computation. They differ only in whether
old K/V tensors are recomputed or reused.

At temperature zero:

```python
assert cached_output == uncached_output == baseline_output
```

This is a strong correctness check because one wrong cache update, position, or
mask can change logits and eventually select a different token.

At temperature above zero, output strings may differ because sampling is random.
Exact comparison then requires controlled random-number state and identical
sampling call order.

## 13. Why the custom attention is monkey-patched

The model normally calls PyTorch's optimized scaled dot-product attention. L2
temporarily replaces that function:

```python
original = F.scaled_dot_product_attention
F.scaled_dot_product_attention = simple_causal_attention

try:
    output = auto_regressive_decode(...)
finally:
    F.scaled_dot_product_attention = original
```

The goal is validation, not speed. If the model produces the same greedy output
with the explicit matrix implementation, the notebook has connected the
attention equation to a real generation path.

The `finally` block is important because monkey-patching changes global process
state. The original function must be restored even if generation raises an
exception.

## 14. Why 11x fewer evaluations produced about 1x speedup

The validated notebook run measured approximately:

| Path | Position evaluations | Time | Throughput |
|---|---:|---:|---:|
| Without KV cache | 264 | 0.33 s | 48.6 token/s |
| With KV cache | 24 | 0.33 s | 48.8 token/s |

This does not contradict the mechanism. For a 1.5B model, a nine-token prompt,
and only 16 generated tokens, runtime can be dominated by:

- Python loop overhead.
- Many small GPU kernel launches.
- GPU synchronization overhead.
- Memory reads and cache management.
- The fixed cost of one forward call per generated token.
- Warm-up and GPU clock variation.

The avoided old-prefix work is small at this sequence length. A longer prompt or
generation makes the redundant uncached work more visible.

L2 synchronizes CUDA before and after timing:

```python
torch.cuda.synchronize()
start = time.perf_counter()
run_decode()
torch.cuda.synchronize()
elapsed = time.perf_counter() - start
```

Synchronization is required because CUDA kernels normally execute
asynchronously. Without it, the CPU timer can stop before GPU work completes.

## 15. Model wrapper mechanics

[`tiny_llm.py`](tiny_llm.py) exposes four relevant operations.

### Standard generation

`generate_std` calls Hugging Face `generate` with `use_cache=True`. It passes the
tokenizer's attention mask and serves as the correctness baseline.

### Tokenize and detokenize

`tokenize` maps text to a Python list of IDs. `detokenize` maps the complete ID
sequence back to readable text.

### Raw forward without cache

`forward_raw` converts the complete token list to a `[1, sequence]` tensor and
calls:

```python
self.model(input_ids, use_cache=False)
```

Explicitly disabling the cache matters. Otherwise the model may construct a
cache that the uncached experiment never uses.

### Raw forward with cache

`forward_raw_with_kv_cache` calls:

```python
self.model(
    input_ids,
    past_key_values=past_key_values,
    use_cache=True,
)
```

It returns final-position logits and the updated cache. The helper passes that
cache into the next decode step.

## 16. Precision and memory

The model loads with `torch.bfloat16`. BF16 uses two bytes per parameter instead
of four for FP32:

$$
M_{weights} \approx parameters \times bytes\ per\ parameter
$$

For 1.5 billion parameters, raw BF16 weights occupy roughly 3 GB. Actual GPU
allocation is higher because inference also needs temporary activations, CUDA
contexts, allocator reservations, and the KV cache.

The educational attention function converts Q, K, and V to FP32 before matrix
operations. This improves numerical stability and readability, but uses more
memory and is slower than the fused production kernel.

## 17. Relationship to SGLang

L2 imports SGLang and prints its version as an environment check, but the model
calls in this notebook go directly through Transformers and PyTorch.

That is intentional for learning. The mechanisms exposed here motivate serving
engine features:

- KV-cache memory management.
- Prefix caching across requests.
- Continuous batching.
- Efficient attention kernels.
- Request scheduling.
- Cache-aware eviction and reuse.

The next conceptual step is prefix caching: if two requests share prompt tokens,
a serving engine can reuse more than each request's private decode cache.

## 18. Limitations of the lesson

L2 isolates mechanisms rather than modeling production serving:

- Batch size is one.
- Manual decoding does not stop early on EOS.
- Only one short prompt is measured.
- The custom GQA implementation copies K/V heads.
- The custom attention does not implement every PyTorch SDPA option.
- There is no concurrency or continuous batching.
- There is no SGLang server process.
- `device_map="auto"` could offload layers on a smaller GPU.

These constraints keep the control flow visible. They should not be used as a
general performance comparison between Transformers and SGLang.

## 19. Experiments that deepen understanding

### Inspect cache growth

After each decode step, print the cache sequence length. Confirm that it grows by
one while `input_ids` passed to the model remains length one.

### Separate prefill and decode timing

Measure:

- Prefill latency.
- Time to first token.
- Mean inter-token latency.
- Total generation latency.

These metrics reveal different parts of the mechanism.

### Sweep prompt length

Keep generated length fixed and test prompt lengths such as 16, 64, 256, and
1024. This increases the old-prefix work avoided by caching.

### Sweep generated length

Keep the prompt fixed and test 16, 64, 128, and 256 generated tokens. Plot both
position evaluations and measured latency.

### Measure cache memory

Record `torch.cuda.max_memory_allocated()` for cached and uncached generation.
The cached path should retain more state even though it performs less repeated
computation.

### Test attention directly

Construct small Q, K, and V tensors and compare the educational function with
PyTorch SDPA. Test both:

- `query_length == key_length`.
- `query_length == 1` with a longer key sequence.

## 20. Mental model to keep

The essential mechanism is:

```text
Prefill:
    all prompt tokens -> all layers -> first logits + initial K/V cache

Decode:
    newest token + old cache
        -> compute new Q/K/V
        -> new Q reads all cached K/V
        -> append new K/V
        -> next-token logits
        -> repeat
```

Without a cache, every decode step rebuilds the old prefix. With a cache, each
layer retains the prefix's K/V tensors and evaluates only the new token position.
The output remains the same; the computation schedule and memory use change.
